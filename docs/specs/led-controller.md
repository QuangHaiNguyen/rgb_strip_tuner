Owner answers to the agent's clarifying questions (collected before drafting, applied throughout this document):

1. **Data pin:** GPIO8 drives the WS2812 data line (GPIO9 is the SPEC-002 provisioning button; GPIO8 is otherwise unused by this project).
2. **Trigger:** On every valid `POST /tuner` submission (SPEC-003), `http_portal` shall, in addition to its existing SPEC-003 FR-17 behavior (validate, log, respond `Sent`), pass the validated `ws2812_timing_t` to `led_controller`, which immediately drives the 6-LED strip with the fixed R/R/G/G/B/B pattern using those timings. The values shall be routed from the HTTP server task to a driver task via a message queue coordinated by the `provisioning` orchestrator (SPEC-002 NFR-9, `main/provisioning/`), not a direct cross-task function call that performs the RMT work. The strip shall also be driven once at boot with the SPEC-003 default timings, before any submission. This spec changes SPEC-003's "no side effects" behavior (FR-19) and "no orchestrator queue message" statement (NFR-13) for a *valid* `/tuner` submission only; SPEC-003 itself is not modified, and its note in NFR-13 ("When a later spec applies the values to a driver task, they shall be passed through a message queue via the `provisioning` orchestrator") is exactly what this spec implements.
3. **Brightness:** A low, fixed, compile-time value of 32/255 on the single active color channel per LED (red LEDs (32,0,0), green LEDs (0,32,0), blue LEDs (0,0,32)), chosen to keep current draw low enough to run from the dev board's USB 5 V supply without an external LED power supply.
4. **Reset time:** The submitted `rst_us` value (from the same `ws2812_timing_t` as bit-0/bit-1 timing) is used as the trailing low period of the generated RMT waveform, so the generated waveform matches the tuner's timing end-to-end.

### 0.2 Agent's Understanding (summary)
This spec adds a new component, `main/led_controller/`, that owns the ESP32-C3's RMT TX peripheral and GPIO8 to drive a 6-LED WS2812 strip with a fixed, hardcoded color pattern (LEDs 0-1 red, 2-3 green, 4-5 blue, each at channel value 32/255) using a *tunable* bit-0/bit-1/reset timing (`ws2812_timing_t`, defined by SPEC-003 in `main/ws2812_timing/`, reused here unmodified). At boot the strip is driven once with SPEC-003's default timing constants. Thereafter, every valid `POST /tuner` submission is forwarded — through the existing `provisioning` orchestrator queue and a new dedicated `led_controller` queue — to re-drive the strip with the newly tuned timing, without blocking the HTTP server task or the orchestrator task during the RMT transmission. The RMT peripheral on ESP32-C3 has no DMA-linked backend (unlike ESP32-S3+); "CPU-free" is achieved through the ESP-IDF RMT TX driver's interrupt-driven symbol refill and asynchronous (non-polling) completion, run entirely inside a dedicated FreeRTOS task so no other task is blocked while a frame is transmitted. The ns-to-RMT-tick conversion and the fixed GRB pixel pattern are implemented as pure, host-testable functions, separate from the RMT driver calls (which are HIL-only). This spec explicitly supersedes SPEC-003 FR-19 and NFR-13 for the "no side effect on a valid submission" behavior only, as anticipated by SPEC-003 NFR-13's own note; SPEC-003's document text is left unmodified and is referenced by ID.

No further interactive clarification was needed in this run; a small number of genuinely new assumptions (RMT resource sizing, task priority/stack, hardware level-shifting) are recorded as open items in section 11.

Per the verified ESP32-C3 pin facts (strapping pins GPIO2/8/9 unavailable — GPIO8 is already `led_controller`'s TX pin, GPIO9 is SPEC-002's provisioning button; flash/PSRAM pins GPIO12-17, USB-Serial/JTAG GPIO18/19, and UART0 console pins GPIO20/21 unavailable), the default/primary mechanism is an external jumper wire from GPIO8 to GPIO4 (a free general-purpose pin), with same-pin loopback (`io_loop_back`) documented as an optional, coding-stage-discretion alternative with a required fallback (section 3.6/section 11). ## 1. Overview

### 1.1 Purpose
SPEC-003 lets the owner discover a working WS2812 bit-0/bit-1/reset timing for a given strip/clone through a web page, but at that stage the ESP32 only logs the values — nothing is driven on a pin. This spec closes that loop for a small, fixed 6-LED test strip: it adds the WS2812 waveform generator (RMT-based, CPU-free) and the fixed fallback/default color pattern needed to visually confirm that a tuned timing set actually lights the physical strip correctly, without yet supporting more LEDs, other colors, or UI-driven brightness/pattern configuration.

### 1.2 Scope
- In scope: a new `led_controller` component that (a) configures GPIO8 and one ESP32-C3 RMT TX channel, (b) drives exactly 6 WS2812 LEDs with a fixed color/brightness pattern (LEDs 0-1 red, 2-3 green, 4-5 blue, each at channel value 32/255), (c) drives the strip once at boot using the SPEC-003 default timing constants, (d) receives a validated `ws2812_timing_t` for every valid `POST /tuner` submission — routed from the HTTP server task through the `provisioning` orchestrator queue and a dedicated `led_controller` queue — and re-drives the strip with it, (e) encodes the WS2812 GRB bit stream and maps nanosecond/microsecond timing values to RMT tick counts through pure, host-testable functions, (f) uses the ESP-IDF RMT TX driver's interrupt-driven, non-blocking transmission so the CPU is not busy-waited during a frame, (g) handles RMT transmit failure without crashing, and (h) serializes/coalesces rapid repeated submissions so at most one pending update is applied per completed transmission. It also covers the small, explicitly scoped changes to `main/http_portal/http_portal.c` (forward the validated timing after FR-17's log line) and `main/provisioning/provisioning.c` (new orchestrator message type and hand-off call) needed to wire the trigger described in owner answer 2. It also covers, per the owner's added requirement (section 0.3), a new `rmt_pulse_monitor` component that (i) owns one of the ESP32-C3's two RMT RX channels and a receive GPIO (GPIO4 by default, jumper-wired to GPIO8, or optionally GPIO8 itself via `io_loop_back`), (j) is armed by `led_controller`'s driver task immediately before every `rmt_transmit()` call so it captures the exact frame just transmitted, (k) decodes the captured symbols back to bit-0/bit-1 classifications through pure, host-testable functions, and (l) prints a compact, bounded set of Info-level measurement lines to the terminal (section 3.6, 7.6).
- Out of scope: more than 6 LEDs, a configurable LED count, configurable color or brightness from the tuner page or any other UI (the pattern and brightness are fixed/hardcoded for this phase — a candidate future extension, see section 11), animations or effects, addressing individual LEDs from the tuner page, persistence of the last-applied timing across reboots (boot always starts from the SPEC-003 defaults, matching SPEC-003's own "no persistence" scope), and any hardware design (level shifter, decoupling capacitor, external 5 V LED supply) — these are noted as hardware risks in section 11, not firmware requirements. For the pulse-measurement addition (section 0.3): out of scope are automated pass/fail gating of the measurement against SPEC-003's tuned tolerance, feeding the measurement back into any control loop or auto-calibration, persistent storage of measurements, and exposing per-symbol data over HTTP. Since 2026-10-03 the terminal output is unchanged and, in addition, a compact summary (average high time per bit and the GRB match count, or the failure kind) is published for SPEC-003's `GET /tuner/result` (FR-34 to FR-37, section 0.4).

### 1.3 Background / Context
- Builds on [SPEC-003](ws2812-tuner-page.md) (`ws2812_timing_t`, `main/ws2812_timing/`, the `POST /tuner` submission handled by `main/http_portal/http_portal.c`) and [SPEC-002](captive-portal.md) (the `provisioning` orchestrator task/queue pattern in `main/provisioning/provisioning.c`, and the `http_portal_ops_t` injection pattern already used for `submit_credentials`/`scan_networks`).
- SPEC-003 FR-19 states that a valid or invalid `POST /tuner` request has "no side effect other than the log line and the HTTP response... no GPIO or peripheral (RMT, SPI, LEDC, timers) configuration or output... no message posted to the provisioning orchestrator queue". SPEC-003 NFR-13 states the same for this stage and adds: "When a later spec applies the values to a driver task, they shall be passed through a message queue via the `provisioning` orchestrator." **This spec is that later spec.** For a *valid* `POST /tuner` submission only, FR-2 of this document supersedes SPEC-003 FR-19's "no side effect" clause and NFR-13's "no orchestrator queue message" clause, exactly as anticipated there. SPEC-003's document text is not edited; it is referenced by ID. A rejected (`400`) `POST /tuner` request and any `GET /tuner` request remain exactly as SPEC-003 describes: no GPIO/peripheral output, no orchestrator message.
- Logging follows [SPEC-001](logging-module.md) through `main/logging/`.
- Firmware rules from [.claude/rules/development.md](../../.claude/rules/development.md) and [CLAUDE.md](../../CLAUDE.md) apply: no `malloc()`/`free()`, Doxygen, Pascal-case verb-first functions, snake_case variables with units, one component per directory with its own `CMakeLists.txt`, dependencies via `REQUIRES`/`PRIV_REQUIRES`, a FreeRTOS task where suitable, inter-task communication via message queue, one orchestrating task.
- Target hardware: ESP32-C3 (RISC-V, single core). The ESP32-C3 RMT peripheral has no GDMA-linked DMA backend (that capability was added starting with ESP32-S3-class chips in later ESP-IDF RMT drivers; the `esp_driver_rmt` component's `rmt_tx_channel_config_t.flags.with_dma` option is not usable on ESP32-C3). "As efficient as possible using DMA or interrupt-based operation" therefore resolves, on this chip, to the ESP-IDF RMT TX driver's interrupt-driven operation: the driver's ISR refills the peripheral's hardware memory blocks from the encoder on the fly and signals completion asynchronously, so the calling task is never required to busy-poll a GPIO or peripheral register waiting for a bit to finish. This is stated as a concrete, testable mechanism in section 4/section 5, not a restatement of the business requirement's vague wording.
- The project's `main/ws2812_timing/include/ws2812_timing.h` already defines `ws2812_timing_t` and the SPEC-003 default constants (`TUNER_DEFAULT_BIT0_HIGH_NS`, `TUNER_DEFAULT_BIT0_PERIOD_NS`, `TUNER_DEFAULT_BIT1_HIGH_NS`, `TUNER_DEFAULT_BIT1_PERIOD_NS`, `TUNER_DEFAULT_RESET_US`). This spec reuses those by name; it does not redefine the type or the default values.
- The project's `main/provisioning/provisioning.c` already has one orchestrator task, one static queue (`s_queue`, `message_t`), and an established "HTTP task calls an `http_portal_ops_t` function → that function posts a message onto the orchestrator queue → the orchestrator's `HandleMessage()` acts on it" pattern (see `SubmitCredentials()`/`MSG_CREDENTIALS_SUBMITTED`). This spec extends that exact pattern rather than inventing a new one.

### 1.4 Definitions & Acronyms
| Term | Definition |
|------|------------|
| RMT | ESP32-C3 Remote Control Transceiver peripheral, used here in TX-only mode to generate the WS2812 waveform. |
| RMT symbol | One `rmt_symbol_word_t`: two (duration, level) pairs, the RMT hardware's atomic waveform unit. |
| Tick | One unit of an RMT symbol's duration field, set by the channel's `resolution_hz` (here 40 MHz, 25 ns/tick, matching SPEC-003 section 5). |
| GRB | The WS2812 per-LED wire byte order: Green byte, then Red byte, then Blue byte, each MSB first. |
| Frame | One complete transmission: 144 GRB-encoded data bits (6 LEDs x 24 bits) followed by one reset (latch) symbol. |
| Channel value | An 8-bit (0-255) intensity for one color channel of one LED; this spec fixes it at 32 for exactly one channel per LED. |
| Timing set | The SPEC-003 `ws2812_timing_t` value (`bit0_high_ns`, `bit0_period_ns`, `bit1_high_ns`, `bit1_period_ns`, `reset_us`). |
| Driver task | The dedicated FreeRTOS task owned by `led_controller` that exclusively performs RMT transmissions. |
| RMT RX channel | The ESP32-C3 RMT peripheral's receive-mode hardware channel (one of two fixed RX channels, distinct from the two fixed TX channels; section 4 NFR-16), used by `rmt_pulse_monitor` to capture the waveform `led_controller` transmits. |
| Idle threshold | The RX channel's end-of-packet detection value (`signal_range_max_ns`): a low period longer than this ends the current capture. Section 3.6 FR-22. |
| Jumper wire / loopback | The two RX wiring mechanisms this spec supports: an external jumper wire between GPIO8 (TX) and GPIO4 (RX, default), or same-pin `io_loop_back` on GPIO8 (optional, section 3.6 FR-21). |
| Decode task | The dedicated FreeRTOS task owned by `rmt_pulse_monitor` that decodes a captured frame and logs the measurement. |

### 3.3 Waveform encoding

| ID | Requirement | Priority | Notes |
|----|-------------|----------|-------|
| FR-9 | `Ws2812NsToTicks(uint32_t duration_ns, uint32_t tick_ns)` shall be a pure function (no ESP-IDF/RMT dependency) computing `ticks = (duration_ns + tick_ns / 2) / tick_ns` (round-half-up), returning a `uint16_t`. | FR-10 | The driver task shall build, per applied timing set, two RMT bit symbols: bit-0 = `{duration0 = Ws2812NsToTicks(bit0_high_ns,25), level0 = 1, duration1 = Ws2812NsToTicks(bit0_period_ns - bit0_high_ns, 25), level1 = 0}`; bit-1 = the same formula using `bit1_high_ns`/`bit1_period_ns`. | FR-11 | The driver task shall build one trailing reset RMT symbol `{duration0 = Ws2812NsToTicks(reset_us * 1000, 25), level0 = 0, duration1 = 0, level1 = 0}` and append it once after the 144 data-bit symbols of one frame. | FR-12 | `BuildLedPixelPattern(uint8_t pixel_grb[LED_CONTROLLER_PIXEL_BYTES])` (`LED_CONTROLLER_PIXEL_BYTES` = 18) shall be a pure function that fills the 18-byte buffer with the fixed pattern of section 7.1 in GRB, MSB-first wire order: bytes 0-2 = LED 0 (red), 3-5 = LED 1 (red), 6-8 = LED 2 (green), 9-11 = LED 3 (green), 12-14 = LED 4 (blue), 15-17 = LED 5 (blue), where LED 0 is the first LED in the physical daisy chain (nearest GPIO8). | Must | This is a deterministic constant-fill function, kept separate from the RMT calls so it is host-testable (T-2). |
| FR-13 | For every applied timing set (boot default or a tuner-submitted update), the driver task shall call `rmt_transmit()` once with the 18-byte buffer of FR-12 and the encoder chain of FR-10/FR-11, producing exactly 144 data-bit symbols followed by the one reset symbol of FR-11 (145 RMT symbols total per frame), then await completion via the driver's non-blocking/asynchronous completion mechanism (`rmt_tx_wait_all_done()` with a bounded timeout, or an `on_trans_done` callback) — never by polling a GPIO level or a busy-wait loop. | Must | "144 bits" = 6 LEDs x 24 bits (FR-12). See section 5 for the CPU-free framing of this requirement (NFR-1). |

### 3.5 Error handling and repeated submissions

| ID | Requirement | Priority | Notes |

| FR-16 | If `rmt_transmit()` returns an error, or the completion wait of FR-13 times out (section 7.4), the driver task shall log the failure at Warning level (transient, e.g. a previous transmission still in flight) or Error level (channel/encoder-level failure), discard the attempted frame, and continue running (wait for the next queued update); it shall not restart the RMT channel, reboot, or crash. ### 3.6 RMT RX pulse measurement (owner's added requirement, section 0.3)
A new component, `main/rmt_pulse_monitor/`, measures the waveform `led_controller` actually generates on GPIO8, by capturing it with an ESP32-C3 RMT RX channel and printing the result to the terminal. `rmt_pulse_monitor` has no dependency on `led_controller` (one-directional: `led_controller` depends on `rmt_pulse_monitor`, NFR-17); it never gates, delays, or blocks a WS2812 frame transmission.

| ID | Requirement | Priority | Notes |
|----|-------------|----------|-------|
| FR-26 | `Ws2812TicksToNs(uint32_t ticks, uint32_t tick_ns)` shall be a pure function (no ESP-IDF/RMT dependency) computing `duration_ns = ticks * tick_ns`, the exact inverse of `Ws2812NsToTicks()` (FR-9) at `tick_ns` = 25 for every tick count this feature produces (no rounding is needed in this direction). | Must | |
| FR-27 | `DecodeWs2812Symbol(rmt_symbol_word_t symbol, uint32_t bit0_high_ns, uint32_t bit1_high_ns, uint32_t tick_ns)` shall be a pure function that (a) rejects the symbol as unclassifiable if `level0` is not 1 (a data-bit symbol's first level shall be high), (b) converts `duration0` to `high_ns` via `Ws2812TicksToNs()` (FR-26), and (c) classifies the symbol as the bit whose commanded (not measured) high time — `bit0_high_ns` or `bit1_high_ns` of the timing set applied for this frame (FR-24's `applied_timing`) — is nearer to `high_ns`, i.e. bit 0 if `|high_ns - bit0_high_ns| <= |high_ns - bit1_high_ns|`, otherwise bit 1. For `bit0_high_ns` < `bit1_high_ns` this is identical to the former midpoint rule (`high_ns <= (bit0_high_ns + bit1_high_ns) / 2` is bit 0). V4 orders duties, not high times. Equal high times are still valid when the bit-1 period is strictly shorter (SPEC-003 vector AC, 500/1250 against 500/1000), so the tie rule and `match=n/a` remain reachable. Inverted high times are still valid when `b1p / b0p < b1h / b0h` (vector AD, 600/2000 against 500/1000), so the inverted case remains reachable. Only equal or inverted high times with equal periods (vectors B and D) can no longer be submitted; they stay covered as pure-function inputs in T-13/T-14. #### 3.6.4 Error handling

| ID | Requirement | Priority | Notes |
|----|-------------|----------|-------|
| FR-31 | The capture timeout applies only after `ArmPulseCapture()` (FR-24) has successfully armed a receive (`rmt_receive()` returned success); while no capture is armed, the decode task waits indefinitely and logs nothing. If the decode task's queue wait (FR-25's capture-done event) times out after `RMT_PULSE_MONITOR_CAPTURE_TIMEOUT_MS` = 20 ms (section 7.5) without a capture-done event, the decode task shall log one Warning line `pulse monitor: capture timed out (reason=no_signal)`, discard any partial state, and return to waiting for the next armed capture; a capture-done event that arrives after the timeout shall be discarded so it is never paired with a later arm. Pairing uses the FR-24 arm sequence number: the decode task, holding the FR-24 RX-channel mutex, decodes an event only if its tag equals the last successfully armed sequence number, and in that case copies the capture buffer and the armed snapshot into its own private storage before releasing the mutex (a bounded copy, so no newer arm can overwrite the data being decoded); a matching event also clears any still-pending arm signal, which can only belong to that same, latest, arm. An event with any other tag is stale: it is discarded (Debug log only) and the wait continues with a fresh `RMT_PULSE_MONITOR_CAPTURE_TIMEOUT_MS` bound, without a timeout Warning or restart. After the timeout Warning, the decode task shall restart the RX channel by calling `rmt_disable()` then `rmt_enable()` (holding the FR-24 RX-channel mutex for the pair), which aborts the pending `rmt_receive()` so the next `ArmPulseCapture()` succeeds; the restart is skipped if a newer capture has already been armed successfully. The "newer capture armed" check compares arm sequence numbers, not the pending arm signal: the decode task records the sequence number it is waiting on (the last armed one when the wait starts, updated to the last armed one when a stale event is discarded); on timeout, holding the RX-channel mutex, it skips the restart only if the last armed sequence number is newer than the one that timed out, and otherwise consumes any still-pending arm signal of the timed-out arm (so it is never waited on a second time) and restarts immediately. Each timed-out arm therefore produces exactly one timeout Warning. If the restart fails, the decode task shall log one Warning `pulse monitor: rx restart failed (err=<code>)` and return to waiting; it shall not retry the restart in a loop, retry the wait, reboot, or crash (a later timeout may attempt the restart again, and the next `ArmPulseCapture()` re-enables a channel left disabled, FR-24). After the timeout Warning, the decode task publishes `timeout` for the `submit_seq` of the arm it was waiting on (FR-35), whether or not the restart runs; it reads that number together with the arm sequence number under the RX-channel mutex, and updates it when a stale event moves the wait to a newer arm (2026-10-03). | Must | Covers a disconnected jumper or an armed capture whose frame never arrives. A failed `ArmPulseCapture()` (FR-24) logs its own Warning and starts no timeout. |
| FR-32 | If a completed capture reports a symbol count other than 144, the decode task shall log one Warning line `pulse monitor: symbol count mismatch (reason=symbol_count count=<n>)` (`<n>` = the actual count) and skip decoding for that capture. If FR-27 finds an unclassifiable symbol among the 144 data-bit positions (`level0` != 1), the decode task shall log one Warning line `pulse monitor: symbol decode error (reason=bad_symbol index=<i>)` (`<i>` = the 0-based symbol index), exclude that symbol from the FR-28 aggregate statistics, and count it as a mismatch in the FR-28(d) comparison; decoding continues for the remaining symbols. Neither condition shall crash, reboot, or trigger a retry storm. A symbol count mismatch publishes `count_error`; a capture with bad symbols is still decoded and publishes `done` (FR-35, 2026-10-03). | Must | The IDF RX driver truncates silently at a full buffer (`rmt_rx.c`, no overflow error), so a longer foreign signal also reports `count=144`: the count check only catches short captures. |

## 4. Non-Functional Requirements

| ID | Category | Requirement |
|----|----------|-------------|
| NFR-1 | Performance / CPU-free operation | From the call to `rmt_transmit()` (FR-13) to the completion signal, the driver task shall not execute a busy-wait loop or poll a GPIO/peripheral register; it shall block on the RMT driver's own completion primitive (`rmt_tx_wait_all_done()`'s internal semaphore, or an equivalent event/callback), during which the FreeRTOS scheduler is free to run other tasks. | NFR-2 | Performance / frame timing | One complete frame (145 RMT symbols: 144 data bits + 1 reset, FR-13) shall take no more than 1.2 ms end to end for any timing set accepted by `ValidateWs2812Timing()` (SPEC-003 section 7.3); worst case (bit period 2,000 ns x 144 + reset 800 us) is 1.088 ms; the SPEC-003 default timing set (period 1,250 ns x 144 + reset 280 us) is 0.46 ms. ## 5. System / Hardware Constraints
- Target: ESP32-C3 (RISC-V single core), ESP-IDF, using the componentized `esp_driver_rmt`/`esp_driver_gpio` (or the umbrella `driver` component, depending on the installed ESP-IDF version — the coding stage shall use whichever the project's ESP-IDF version exposes, keeping the `rmt_tx.h`-based API described here).
- RMT resource usage: one TX channel, `resolution_hz` = 40,000,000 (25 ns/tick, exact at both the 40 MHz XTAL clock source and an 80 MHz APB source divided by 2 — matches SPEC-003 section 5's reasoning so the tuner's 25 ns step and 10 us reset step always convert to an exact tick count, FR-9). `trans_queue_depth` = 1 (this feature only ever has one frame outstanding at a time; FR-17's queue is the application-level coalescing point, not the RMT driver's internal transaction queue). `mem_block_symbols` = 48 (`SOC_RMT_MEM_WORDS_PER_CHANNEL` on ESP32-C3): exactly one hardware block per channel. A larger value (e.g. the driver's documented default of 64) is rounded up to two blocks and also occupies the neighbouring channel's block, leaving no channel free (NFR-16). One block is sufficient because the bytes encoder streams data via the driver's own ISR refill (24-symbol ping-pong halves) rather than requiring the whole 145-symbol frame to be pre-resident in RMT hardware memory.
- DMA: not used and not available for RMT on ESP32-C3 (section 1.3). Efficiency is achieved through the RMT driver's interrupt-driven symbol refill and asynchronous completion (NFR-1), not through busy-waiting or GPIO bit-banging (FR-8, FR-13).
- GPIO8: dedicated to the WS2812 data line (owner answer 1); not driven as a plain GPIO output by this feature (FR-8); not used by any other component (FR-3).
- Frame timing budget: worst case 1.088 ms, typical (SPEC-003 defaults) 0.46 ms, both far below any FreeRTOS tick-scheduling concern on this project's tasks (NFR-2).
- Power: no external LED power supply is required at the chosen brightness (NFR-3); this is a firmware-level current estimate, not a hardware qualification of the USB supply path (section 11).

### 5.1 RMT RX pulse measurement (owner's added requirement, section 0.3)
- RMT resource usage: one RX channel (of the SoC's two fixed RX channels, group channels 2-3), `resolution_hz` = 40,000,000 (25 ns/tick, matching the TX channel, FR-19/section 7.5), `signal_range_min_ns` = 50, `signal_range_max_ns` = 25,000 (FR-22), `mem_block_symbols` = 48 (one hardware block; the RX ping-pong ISR copies each 24-symbol half into the FR-23 buffer as it fills, so all 144 symbols stream through one block). Zero conflict with `led_controller`'s TX channel (group channels 0-1, NFR-16).
- ESP32-C3 GPIO pin designation used for this decision (verified against the ESP32-C3 datasheet/technical reference manual, section 13):

  | GPIO | Designation | Available for RX? |
  |------|-------------|--------------------|
  | 0 | General-purpose; commonly wired to a BOOT button on dev kits (board-level, not a functional strapping conflict) | Free (not chosen, precautionary) |
  | 1, 3, 5, 6, 7, 10 | General-purpose, no known reservation in this project | Free |
  | **4** | **General-purpose, no known reservation in this project** | **Chosen (`RMT_PULSE_MONITOR_RX_GPIO_NUM`, FR-19/FR-21)** |
  | 2, 8, 9 | Strapping pins (`GPIO_STRAPPING`, `GPIO_STRAP_REG`); GPIO8 = `led_controller` TX (FR-3), GPIO9 = SPEC-002 provisioning button | Not available |
  | 12-17 | SPI flash/PSRAM | Not available |
  | 18, 19 | USB-Serial/JTAG (default) | Not available |
  | 20, 21 | UART0 console (SPEC-001 logging) | Not available |

- Default RX wiring: an external jumper wire from GPIO8 to GPIO4 on the dev board (FR-21). This is a physical test-setup requirement for HIL testing (section 10), not a firmware requirement, and is required in addition to `led_controller`'s existing WS2812 strip wiring on GPIO8 (T-8, T-9).
- Optional RX wiring (coding-stage discretion): `io_loop_back` on GPIO8, no external wire (FR-21); carries the unconfirmed-on-ESP32-C3 risk noted in section 11 (espressif/esp-idf#11768) and requires the same HIL validation (T-15) before being relied upon.
- Frame/capture timing: one capture completes no later than the transmitted frame's duration (led-controller section 5, up to 1.088 ms worst case) plus the 25,000 ns idle threshold; the decode task's bounded wait (FR-31) is 20 ms, well above this.

## 7. Data & Configuration

### 7.1 Fixed color/brightness pattern and current-budget justification
| LED index (0 = nearest GPIO8) | Color | R | G | B | Wire bytes (GRB) |
|---|---|---|---|---|---|
| 0 | Red | 32 | 0 | 0 | `00 20 00` |
| 1 | Red | 32 | 0 | 0 | `00 20 00` |
| 2 | Green | 0 | 32 | 0 | `20 00 00` |
| 3 | Green | 0 | 32 | 0 | `20 00 00` |
| 4 | Blue | 0 | 0 | 32 | `00 00 20` |
| 5 | Blue | 0 | 0 | 32 | `00 00 20` |

`LED_CONTROLLER_CHANNEL_VALUE` = 32 (of 255, about 12.5% of full channel intensity). Current-budget estimate (informational, not a controlled measurement — see NFR-3, T-10): typical WS2812B datasheet figures cite about 20 mA per color channel at full (255) intensity. At value 32, one lit channel draws approximately `20 mA x 32/255` ~= 2.5 mA. Because the fixed pattern lights exactly one channel per LED (never two or three), each LED draws about 2.5 mA plus roughly 1 mA of WS2812B controller-IC quiescent current, ~= 3.5 mA per LED. Six LEDs total ~= 21 mA, well under a typical USB port/regulator's 500 mA budget, satisfying the "no external LED supply" goal of owner answer 3.

### 7.2 Waveform mapping
```
tick_ns = 25                                    (40 MHz RMT resolution_hz)
ticks(duration_ns) = round_half_up(duration_ns / tick_ns) = (duration_ns + tick_ns/2) / tick_ns

bit0 symbol = { duration0 = ticks(bit0_high_ns),                level0 = 1,
                duration1 = ticks(bit0_period_ns - bit0_high_ns), level1 = 0 }
bit1 symbol = { duration0 = ticks(bit1_high_ns),                level0 = 1,
                duration1 = ticks(bit1_period_ns - bit1_high_ns), level1 = 0 }
reset symbol = { duration0 = ticks(reset_us * 1000),             level0 = 0,
                 duration1 = 0,                                  level1 = 0 }

frame = 6 LEDs x 24 bits (GRB, MSB first per byte) = 144 data-bit symbols, then 1 reset symbol (145 total).
```
Worked example (SPEC-003 defaults): bit0 = {16,1,34,0} (400/25=16, 850/25=34); bit1 = {32,1,18,0} (800/25=32, 450/25=18); reset = {11200,0,0,0} (280,000/25=11,200).

### 7.6 Pulse-measurement log line formats (Info level, at most 127 characters each, owner's added requirement, section 0.3)
```
Line 1 (bit examples):    "pulse: bit0 first high_ns=%u low_ns=%u; bit1 first high_ns=%u low_ns=%u"
Line 2 (aggregate stats):  "pulse: bit0 high_ns min=%u max=%u avg=%u; bit1 high_ns min=%u max=%u avg=%u"
Line 3 (match):            "pulse: grb match=%u/144"
Line 3 (equal high times): "pulse: grb match=n/a"
```
Example output (SPEC-003 default timing set, an ideal capture with no measurement error):
```
pulse: bit0 first high_ns=400 low_ns=850; bit1 first high_ns=800 low_ns=450
pulse: bit0 high_ns min=400 max=400 avg=400; bit1 high_ns min=800 max=800 avg=800
pulse: grb match=144/144
```
All three lines are emitted together, once per successfully decoded capture (FR-29/FR-30). Values are unsigned decimal integers with no leading zeros, matching SPEC-003 FR-17's log-value style. Line 3's longest form (`pulse: grb match=144/144`) is well under the 127-character limit. When the applied bit-0 and bit-1 high times are equal, line 3 is exactly `pulse: grb match=n/a` and lines 1-2 report bit-0/bit-1 values partitioned by the expected bit (FR-28). The reset time is not logged because it is not measurable in a single-frame capture (FR-23). These lines are unchanged by the 2026-10-03 revision; the same capture also yields the published summary (line 2's two `avg` values and line 3's match count or `n/a`, FR-35).

## 8. Behavior / Use Cases

### 8.1 Use Case: Boot-time default drive
- **Actor:** Firmware at startup.
- **Preconditions:** `app_main()` has called `LogInit()`.
- **Main flow:**
  1. `app_main()` calls `StartLedController()` (FR-1).
  2. GPIO8/RMT channel/encoders/task/queue are created; the driver task (or the calling context, per the coding stage's chosen synchronous/asynchronous split) drives one frame with the SPEC-003 default timing set and the fixed color pattern.
  3. `app_main()` calls `ProvisioningStart()`.
- **Postconditions:** The strip shows the fixed R/R/G/G/B/B pattern at the default WS2812B timing before any network activity.
- **Alternate/Error flows:** If step 2 fails (FR-2), the strip stays dark; provisioning still starts (step 3 still runs).

### 8.2 Use Case: Tuner submission re-drives the strip
- **Actor:** User with the SPEC-003 tuner page open, having just pressed `Send`.
- **Preconditions:** `StartLedController()` succeeded; the tuner is served by either HTTP server profile: provisioning mode (SPEC-003 FR-2) or station mode (SPEC-005 FR-11 to FR-13). (Updated 2026-10-03; the original "provisioning mode is active" is superseded by SPEC-005.)
- **Main flow:**
  1. Browser issues `POST /tuner` (SPEC-003 FR-11/FR-14).
  2. `http_portal` parses and validates the body (SPEC-003 FR-15/FR-16), logs the Info line (SPEC-003 FR-17), then calls `ops->apply_led_timing(&timing, submit_seq)` (FR-4).
  3. `provisioning` posts `MSG_LED_TIMING_SUBMITTED` onto its orchestrator queue (FR-5) and `http_portal` immediately responds `200 Sent` (SPEC-003 FR-17) without waiting for steps 4-6.
  4. The orchestrator task dequeues the message and calls `ApplyWs2812Timing()` (FR-6), which overwrites the driver task's 1-deep queue and returns (FR-7).
  5. The driver task wakes, builds the bit-0/bit-1/reset symbols (FR-10/FR-11) and the (unchanged) fixed pixel buffer (FR-12), and transmits one frame (FR-13).
  6. The strip re-lights with the fixed pattern at the newly tuned timing.
- **Postconditions:** The strip reflects the latest valid submission; the HTTP response and SPEC-003's UART log are unaffected by how long step 5-6 take. The measurement outcome is published for that number (FR-35).
- **Alternate/Error flows:** A `400` rejection (SPEC-003 FR-18) never reaches `apply_led_timing` (FR-4); the strip is unchanged. In particular a SPEC-003 `bad_duty_order` rejection produces no frame and no capture (SPEC-003 FR-22).

### 8.3 Use Case: Rapid repeated submissions
- **Actor:** User pressing `Send` multiple times in quick succession (or two browser tabs submitting close together).
- **Main flow:** Each valid submission reaches `ApplyWs2812Timing()` (use case 8.2). If the driver task is still transmitting/waiting when a second (or third) update arrives, `xQueueOverwrite()` replaces the pending value (FR-17); once the current frame finishes, the driver task applies only the latest queued value.
- **Postconditions:** The strip converges on the timing set from the most recent submission; intermediate submissions between two RMT frames are not separately visible on the strip, but each still produced its own SPEC-003 log line and HTTP response. Only the latest request's number is armed and published; overwritten numbers are reported as `superseded` by SPEC-003 (FR-33).

### 8.4 Use Case: RMT transmit failure
- **Actor:** Driver task, on a hardware/driver-level error.
- **Main flow:** `rmt_transmit()` or the completion wait fails (FR-13); the driver task logs at Warning or Error level (FR-16) and returns to waiting on its queue.
- **Postconditions:** No crash; the strip keeps showing its last successfully transmitted frame; the next successful update (boot retry is out of scope — the next tuner submission) proceeds normally.

### 8.5 Use Case: Pulse measurement of a transmitted frame (owner's added requirement, section 0.3)
- **Actor:** `rmt_pulse_monitor`, triggered internally by `led_controller`'s driver task.
- **Preconditions:** `StartPulseMonitor()` succeeded (FR-19/FR-20); the RX GPIO is jumper-wired to GPIO8 (default) or `io_loop_back` is enabled (FR-21).
- **Main flow:**
  1. `led_controller`'s driver task is about to drive a frame (boot default, use case 8.1, or a tuner re-drive, use case 8.2).
  2. It calls `ArmPulseCapture()` (FR-24) with the timing set and pixel buffer about to be transmitted, then calls `rmt_transmit()` (FR-13) as before.
  3. The RX channel captures the same waveform on GPIO4 (or GPIO8 in loopback mode) into the static buffer (FR-23).
  4. On completion (idle threshold reached, FR-22), the `on_recv_done` callback (FR-25) signals the decode task.
  5. The decode task decodes and logs the three Info lines of section 7.6 (FR-26 to FR-30), then publishes the outcome (FR-35).
- **Postconditions:** The terminal shows the measured pulse characteristics for that frame; no other system state changes (out of scope, section 1.2).
- **Alternate/Error flows:** Capture timeout (FR-31) or symbol-count/decode error (FR-32) produce Warning logs with no crash; a `StartPulseMonitor()` failure (FR-20) means no capture is ever attempted and `led_controller` is unaffected. A timeout publishes `timeout`, a count mismatch `count_error`, and an arm skip or failure or a monitor that is not running publishes `not_measured`; a frame skipped by `led_controller` before arming publishes nothing (FR-35, FR-36).

This spec does not rely on loopback working: it is optional, and the jumper-wire design (FR-21 default) is unaffected by this uncertainty. | If the coding stage attempts the optional loopback path first without validating it against T-15, a non-working measurement path could be mistaken for a `led_controller` TX fault. | FR-21's mandatory fallback to the jumper design; T-15 must pass before either path is considered done. |
| Design correction after target testing (owner-approved): on the wire, the WS2812 reset low is contiguous with the last data bit's low (no edge between them), so it is not a separate RX symbol, and the RX channel ends the capture once the line is idle longer than `signal_range_max_ns` (25 us, FR-22). A capture therefore always holds exactly 144 symbols, and the final symbol's `duration1` is the RMT end marker (0). | The reset time and the final bit's low time cannot be measured from a single-frame capture. | FR-23/FR-28/FR-29/FR-32 expect 144 symbols, drop the reset measurement, and never read the final symbol's `duration1` as a low time. The TX frame is unchanged (FR-11/FR-13); the reset can still be checked with a logic analyzer (T-8). |
| Design decision (owner-approved, 2026-09-27): a capture timeout (e.g. jumper pulled) previously left the `rmt_receive()` pending, so every later `ArmPulseCapture()` failed with `arm failed (err=...)` until reboot. In ESP-IDF v6.0-beta2, `rmt_disable()` is accepted in both the enable and run states and returns the channel to init with its RX interrupts masked and cleared, and `rmt_enable()` makes it armable again; there is no dedicated abort API. | Without a restart, measurement never recovers; the restart and `rmt_receive()` both change the RX channel's driver state and must not interleave. | FR-31 restarts the RX channel after a timeout under an RX-channel mutex shared with `ArmPulseCapture()` (FR-24), which takes it with a zero timeout and skips arming with a Warning if busy. A failed restart logs one Warning; no retry loop, no reboot. |
| Review M-1 (owner-approved, 2026-09-28): on ESP32-C3 one RMT hardware block holds `SOC_RMT_MEM_WORDS_PER_CHANNEL` = 48 symbols. With `mem_block_symbols` = 64 the driver (`rmt_tx.c`/`rmt_rx.c`, `rmt_*_register_to_group()`) rounds up to two blocks, so the TX channel took channels 0-1 and the RX channel 2-3, leaving none free (contradicting NFR-16). | No RMT channel left for other uses; the ISR refill/copy now works in 24-symbol halves instead of 48, halving the interrupt-latency slack per half. | `mem_block_symbols` = 48 on both channels (section 5/5.1). TX refill and RX ping-pong both stream the frame through one block. Re-verify on hardware that an ideal frame still reports `grb match=144/144` (T-15). |
| Review M-2 (owner-approved, 2026-09-28): NFR-4/NFR-13 counted the static task stacks (3,072 and 2,048 bytes) against 1,024/2,048-byte `.data`/`.bss` budgets, which the stacks alone exceed. | The budgets could not be met as written. | The budgets exclude task stacks; stacks are budgeted by their section 7.4/7.5 sizes. |
| Review M-3 (owner-approved, 2026-09-28): the midpoint rule (bit 0 if high time <= midpoint) read every bit inverted for SPEC-003 vector D (bit-0 high > bit-1 high) and could not distinguish bits for vector B (equal highs), yet reported a count. | Misleading `grb match` results for valid timing sets. | FR-27 nearest-commanded-high-time rule with a bit-0 tie rule; FR-28/section 7.6 report `match=n/a` for equal high times, with statistics partitioned by the expected bit. |
| Review race fix (owner-approved, 2026-09-28): the armed snapshot and capture buffer were shared between the driver task (priority 4) and the decode task (priority 2) without protection, and `xQueueReset()` on arm could drop a valid, unconsumed done event, shifting the arm/event pairing by one (spurious timeout and restart). | Wrong-snapshot decode or a spurious timeout/restart. | Arm sequence number (FR-24/FR-25/FR-31): events are tagged by the ISR, stale events are discarded, and the decode task copies the matched data under the RX-channel mutex. `ArmPulseCapture()` stays non-blocking (zero-timeout take, NFR-12). |
| Unconfirmed assumption (new in this addition): the decode task's priority (2), stack size (2,048 bytes), and the capture-timeout margin (20 ms, section 7.5) are agent-proposed defaults, not measured. | Too small a stack could overflow; too tight a timeout could cause a spurious Warning under scheduling jitter. | Verify stack high-water mark and timeout margin during T-15/T-16; adjust before merge if needed. |
| Unconfirmed assumption (new in this addition): the GRB match/mismatch reporting (FR-28d) assumes the expected pattern equals `led_controller`'s currently-applied fixed pixel buffer, passed at arm time (FR-24). This is diagnostic only and is explicitly not fed back into any control loop (section 1.2). | None functionally; documented for clarity. | No action needed by design; a future spec could repurpose this comparison for automated pass/fail gating, which is explicitly out of scope here. |
| Accepted by the owner (2026-10-03): reachability after SPEC-003 V4. V4 removes only equal or inverted high times with equal periods (vectors B and D) from the `/tuner` path. Equal highs with a shorter bit-1 period (AC) and inverted highs with a sufficiently shorter bit-1 period (AD) still reach the strip. | A reader could think the tie rule and `n/a` are now dead code. | Closed. The decode rule is unchanged; AC and AD are in T-8, T-13, T-14 and T-21; B and D stay as pure inputs. |
| Accepted by the owner (2026-10-03, "Accept (Recommended)"): two producers of outcomes (the driver task for `not_measured`, the decode task for the rest) can post out of number order, e.g. arm 6 skipped while the decode task still holds 5's copy. Only the latest result is kept. | 5's measured result is dropped by SPEC-003's monotonic setter, and 5 reads `superseded`. | Closed (SPEC-003 FR-24, section 11). |
| Accepted by the owner (2026-10-03): "I want to have this: If you'd rather the page just time out with Measurement not available after about 2 s, that's a small revert." Frames that `led_controller` skips before arming (previous frame still in flight, encoder update failure, FR-16) publish no result; SPEC-003's poll returns `state=pending` until its 8-poll limit and the page shows `Measurement not available` after about 2 s, or `superseded` once a newer outcome is stored. `not_measured` stays for arm skipped, arm failed and monitor not running (FR-36). | About 2 s of waiting in rare error paths that already log a Warning or an Error. | Closed. Verified by T-19 (no callback on a pre-arm skip) and T-20. |
| Design note (2026-10-03): the FR-34 callback pointer is read without a lock. | None on the ESP32-C3 (aligned word); it is written once before any submission. | Same argument as `s_capture_seq`; reviewed in T-20. |
| Out of scope for this phase, owner's added requirement (recorded per guidance, not a defect): automated pass/fail gating of the measurement against SPEC-003's tuned tolerance, feeding the measurement back into any control loop or auto-calibration, persistent storage of measurements, and exposing per-symbol data over HTTP (since 2026-10-03 a compact summary is exposed, FR-34 to FR-37). | The owner may want these later. | A future spec can extend this; FR-26 to FR-28's pure-function boundary is designed to make that extension straightforward, mirroring `led_controller`'s own `BuildLedPixelPattern()` precedent. |
